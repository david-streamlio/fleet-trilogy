01

Methodology

Two structurally different jobs were asked of small models in this deployment, and they needed different evaluation designs and produced different failure shapes. Conflating them is the first mistake practitioners tend to make.

1.1Two task shapes, not one

Judgment task (referred to below as the Edge Triage Pipeline): a deterministic pipeline computes a baseline severity and hands the model three free-text operational fields (weather, cargo, dispatch status). The model's only job is a bounded three-way decision — raise, hold, or lower that baseline — which requires weighing several soft signals against each other. This is reasoning, not lookup.

Paraphrase task (Tier 2): scope and any reroute decision are already fully decided by plain code before the model is ever invoked. The model's only job is to phrase those already-settled facts as two or three natural, speakable sentences. It never decides anything — its failure modes are fidelity failures (omitting a fact, inventing one, or failing to paraphrase at all), not judgment errors.

The same model can fail one of these tasks and pass the other outright — see §5.3. Treating "how good is this model" as one number, independent of task shape, is the single most common way this kind of evaluation goes wrong.

1.2A two-stage funnel

Every model passed through a quality gate on fast hardware (an M4 Max workstation) before ever touching the real deployment target (a Raspberry Pi 4, 8GB RAM, 4 cores). The M4 gate is fast and cheap to iterate on, but its latency and RAM numbers are meaningless for the actual deployment — only the target hardware's own numbers are decision-grade. Skipping the second stage and shipping on M4-only numbers would have shipped at least one model (Qwen3-8B, Tier 2) whose passing grade turned out to be an artifact of a config choice never exercised on the real target — see §2.5.

2.4Case study: thermal throttling silently caps edge performance

Mid-run, the Pi's own thermal state was checked directly rather than assumed. Under sustained inference load it was measurably throttling — and this had been true the whole time, undetected.

600MHz is one-third of the confirmed 1800MHz stock boost clock — a real ~67% reduction, not a rounding artifact. This had been quietly attributed to one specific, unusually large model's weight class; the reading above was taken on a completely different, much smaller model, under ordinary sustained load. A single physical fan restored full clock speed.

Takeaway

Any edge latency number gathered without checking throttle state at the same time is a number of unknown provenance — it may describe the hardware's real capability, or an arbitrarily throttled fraction of it. Check vcgencmd get_throttled (or the equivalent on your target) on every run, not only when something already looks slow.

2.5Case study: a generous token budget can hide a real defect

One model's Pi run initially collapsed to 10% successful completions — every failure timing out at exactly the configured limit. The fix (correctly wiring the timeout, then capping the token budget to what the task actually needs) recovered successful completions to 100% — but then exposed a second, unrelated, genuine defect that a looser budget had been masking on both hosts all along.

ModelHostToken budgetStructured rateSpeakability violationVerdict
Qwen3-8BM4256 (original)90.0%10.0%PASS
Qwen3-8BM4110 (corrected)73.3%26.7%REJECT
Qwen3-8BPi110 (corrected)63.3%36.7%REJECT

Reading the actual output explained why: this model reasons out loud before answering ("Alright, let's see. The user wants a proactive traffic warning…") in a raw-completion setup with no chat template to separate thinking from the final answer. A budget generous enough to let it finish thinking looked like a clean pass; a budget sized for what the target hardware can actually afford exposed that it doesn't reliably reach the answer at all. The same regression on both hosts under the identical corrected config is what proves this is a real model/configuration interaction, not a hardware artifact — see §5.5.

03

Prompt engineering, quantified

Five independent prompt-side attempts to move accuracy, across two different tasks and two different kinds of intervention (rewriting rules, and adding worked examples). Every one of them produced the same underlying failure shape at least once: a change that measurably fixes one weakness collapses a different scenario or a different model into a constant, degenerate answer.

3.1The diagnostic that made this visible: break the aggregate open

A single mismatch-rate number looks like one axis of quality. Net verdict

Out of five independent prompt-side accuracy interventions tested across two tasks, exactly one (the rule-engine rewrite, on Llama-3.1-8B only) produced an unambiguous win with no matching cost. Every other one either produced a mixed result with a real hidden cost, or made the aggregate number worse while looking like a win on the one dimension it targeted. This is not a story about picking the wrong wording — it recurred across rule-tightening and worked examples, across two unrelated tasks, on five different models. Treat it as a structural property of pushing more instruction-following load onto a small model, not a bug to word your way out of. Full detail in §5.2.

04

Data engineering, quantified

What you feed a model changed outcomes more reliably than how you word the instruction asking for them — but the effect was real, conditional, and had to be measured per model, per signal. It was never a universal lever.

Average improvement across the full 15-model spectrum from the velocity fix: 7%. Two real, physically-grounded signals, tested against the same three small models, produced a win, a regression, and a wash — for the same model on the same task, depending only on which real signal was handed to it.

Takeaway

"Feed the model real data" is necessary but not sufficient. Which real signal helps which specific model is not reliably predictable in advance — it has to be measured per model, per signal, not assumed from one success.

4.3The architectural pivot — the single largest win in this report

Ten-plus rounds of prompt tuning tried to make small models classify event severity directly from raw signals. Every round hit the same ceiling: mismatch rates from 33% to 73%, with degenerate constant-output collapse as the norm, not the exception. The fix was not a better prompt — it was removing the job from the model entirely. A deterministic, hand-verified classification function now computes severity instantly, for free, with zero model dependency.

10+ rounds of prompt tuningDeterministic classification
Severity mismatch rate33–73%, never solved0% — by construction
Model dependencyYes — every model behaved differentlyNone
recommended_action / escalation contradictionRecurred under 3 separate wording fixesEliminated by construction

The model's job narrowed to the one genuinely unstructured decision left — a bounded escalate/hold/lower call over free-text operational context — and that narrower task is where the five-model clean tier in §2.2 comes from. The lesson generalizes past this one pipeline: before spending another round tuning a prompt, ask whether the sub-task is actually reducible to code. If it is, that beats every prompt-side fix tried on it.

05

Pitfalls for practitioners

The concrete, recurring failure modes worth planning for before deploying small LLMs on resource-constrained hardware — each one cost real time to diagnose in this project.

1

An aggregate accuracy number can hide a 100% failure on one dimension

One model's overall mismatch rate looked fine while it scored 0% correct on an entire severity tier, invisible in the rolled-up number because it compensated elsewhere. Always check the full per-scenario or per-tier breakdown, never just the headline rate.

Gemma-3-1B-it: 47.8% aggregate mismatch (a pass) alongside 0% correct on its "low" tier, every round tested
2

Overcorrection is systemic, not a wording bug

Sharpening an instruction to fix one model's specific failure — whether by tightening rules or by adding worked examples — repeatedly collapsed a different scenario, or a smaller model, into a constant, degenerate answer. This happened five separate times across two unrelated tasks and two different intervention types. Budget for this risk on every prompt change; don't treat any single fix as safe until checked per-scenario.

See §3 — five distinct instances, same underlying shape each time
3

Task-appropriate sizing beats "use the biggest model"

The same model, same weights, same day: unusable for one task and cleanly production-viable for a different one. Model choice has to be made per task, not once for a whole pipeline.

Gemma-3-1B-it: 51.1% mismatch on the judgment task (rejected) vs. 10.0% grounding violation on the paraphrase task (passed cleanly)
4

Thermal throttling silently corrupts edge latency measurements

Sustained inference load throttled the target device's clock to a third of its rated speed, with no visible symptom besides "it's slow." Any latency number collected without checking throttle state at the same time is a number of unknown provenance.

83.7°C, throttle bits live-set, clock at 600MHz of a confirmed 1800MHz stock boost — recovered fully with a single added fan
5

A generous token budget can mask a real quality defect

A model's clean pass turned out to be an artifact of unused headroom in its output length limit, not evidence it actually completes the task reliably. Size generation limits to what the target hardware can afford, not to whatever the fast dev machine can tolerate — a tighter, realistic budget is itself part of the test.

Qwen3-8B: PASS at a 256-token budget, REJECT at a 110-token budget sized for the actual answer — on both the dev machine and the target device
6

Measurement infrastructure fails about as often as the models do

Five distinct, real bugs in the evaluation harness itself — not the models — produced or would have produced wrong conclusions if not caught: a stop-sequence/grammar interaction that silently truncated every completion, a crash that discarded an entire run's results before they were written to disk, a stale schema check that would have reported 0% reliability for every model, a CLI timeout flag that was read but never actually applied, and two grounding checks that scored genuinely correct answers as failures. Treat "the model failed" and "the harness has a bug" as equally likely hypotheses until the raw output is actually read.

7

Retrieval and few-shot examples are not free, and are not guaranteed wins

Retrieval-augmented prompting added a measurable, real memory and load-time cost with no measurable accuracy benefit on the model it was tested against. Static few-shot examples, its cheaper cousin, produced one real net win and one outright regression on the two models tested. Neither technique should be assumed to pay for itself — measure the specific model and specific failure mode before adopting either.

RAG: 4.91s embedder load + 532MB RSS for a 1.1-percentage-point accuracy change (noise). Static few-shot: one model improved 45.1%→27.3%, a different model worsened 50.0%→63.3%

6.2A decision framework

Never ship on the quality-gate host's numbers alone. Run the quality gate on whatever hardware is fast to iterate on, then confirm every candidate on the actual target device before calling anything decision-grade — speed, RAM, thermal behavior, and even some accuracy regressions only show up there.

Split judgment from paraphrasing wherever a pipeline does both. A model that reasons about ambiguous context and a model that faithfully restates already-decided facts are different jobs with different minimum capability bars — evaluate and select for each separately.

Before tuning a prompt again, ask whether the sub-task is really a judgment call. If it reduces to a deterministic function of the inputs, moving it to code outperforms every prompt-side fix tried on it in this report, with zero model dependency and zero recurring latency cost.

Treat every prompt change as a regression test across every scenario, not a targeted patch. The one axis you're trying to fix is the one axis least likely to reveal a new collapse; check the others every time.

Every number in this report is a real measurement against real models on real hardware — M4 Max workstation and Raspberry Pi 4, llama.cpp/GGUF, Q4_K_M and Q8_0 quantization — not a projection. Sample sizes and artifact provenance are noted inline; several results are explicitly flagged as small-sample and plausibly noisy rather than presented as more certain than they are.
